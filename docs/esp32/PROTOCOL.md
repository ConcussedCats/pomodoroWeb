# Telos ⇄ ESP32 Pomodoro Flip Cube — protocol v1

This document is the contract between the Telos backend, the Telos web client and
the ESP32 firmware. Everything here is implemented on the server side and covered by
automated tests against a software emulator (`tools/esp32-emulator`). Nothing here
has been verified on real hardware yet — see [HARDWARE-CHECKLIST.md](HARDWARE-CHECKLIST.md).

* Protocol version: `1` (sent by the device as `protocolVersion`)
* Transport: HTTPS + JSON (UTF-8). All timestamps are **epoch milliseconds (UTC)**.
* Onboarding transport: Bluetooth Low Energy GATT (see [BLE-GATT.md](BLE-GATT.md)).

---

## 1. Shared timer contract

### 1.1 Modes

| Server / device | Web (`timer-state.js`) | Cube face     |
|-----------------|------------------------|---------------|
| `WORK`          | `pomodoro`             | `WORK`        |
| `SHORT_BREAK`   | `short-break`          | `SHORT_BREAK` |
| `LONG_BREAK`    | `long-break`           | `LONG_BREAK`  |

### 1.2 Statuses

| Status     | Meaning                                                           |
|------------|-------------------------------------------------------------------|
| `RUNNING`  | Counting down. `startedAt` + `remainingSeconds` define the end.   |
| `PAUSED`   | Frozen. `pausedAt` is set, `remainingSeconds` is the frozen value.|
| `STOPPED`  | Idle / reset. `remainingSeconds == durationSeconds`.              |
| `FINISHED` | Countdown reached zero. Waits for the user to choose the next mode.|

`PAUSE` is a command and a status, never a session type or a duration.

### 1.3 Timer state snapshot

Used in events, command acknowledgements, heartbeats and WebSocket messages.

```json
{
  "mode": "WORK",
  "status": "RUNNING",
  "durationSeconds": 1500,
  "remainingSeconds": 1500,
  "startedAt": 1761150000000,
  "pausedAt": null,
  "sessionId": "b0c5b9b2-3f3e-4a7e-9f2a-1f1d3c2b4a59",
  "cycleIndex": 0,
  "phaseIndex": 0
}
```

* `remainingSeconds` is the remaining time **at `startedAt`** while `RUNNING`, and the
  frozen remaining time while `PAUSED`. The countdown is never sent every second:
  each side computes `endsAt = startedAt + remainingSeconds * 1000` locally.
* `startedAt` — when the current running segment began (reset on every resume).
  A device without a synced clock sends `startedAt: null` and the server counts from
  the moment it received the report.
* `sessionId` — UUID generated by whoever starts a new countdown (the device in
  Connected Device Mode). It identifies one Pomodoro session for history and is the
  de-duplication key; resuming keeps the same `sessionId`.
* `cycleIndex` / `phaseIndex` — position in the user's `classic` / `compact` pattern.
  They are **owned by the server** (see 1.5); the device echoes what it last received
  and may omit them.

The server adds `version` (monotonic integer, +1 on every accepted change),
`updatedAt`, `suggestedNextMode`, `totalCycles` and `patternType` when it returns state.

### 1.4 Connected Device Mode vs Standalone Mode

* **Standalone Mode** (default, no device selected): the browser timer works exactly
  as before — `localStorage`, automatic phase transitions, classic / compact patterns,
  cross-tab sync. The server is not involved except for saving settings and history.
* **Connected Device Mode** (a device is selected on the timer page): the cube is the
  only thing that counts down. The browser renders the server state and sends
  **commands**; it never changes the timer state by itself. The server changes the
  timer state only from what the device reports (events and command acks).
  So there are never two independent timers.

Switching rules (enforced by the web client):

1. Standalone → Connected: if the browser timer is running it is paused first
   (its `localStorage` state stays as it was and comes back when you switch back).
2. Connected → Standalone while the cube is `RUNNING`: the user must confirm and a
   `STOP` command is sent, or the switch is cancelled.
3. Unbinding a device ends Connected Device Mode in every tab.

### 1.5 Phase pattern in Connected Device Mode

The server uses the same pattern tables as `timer-state.js`
(`classic`: W S W S W S W L, `compact`: W S W L, repeated `pomoCycles` times) and the
same skip rule for manual overrides. Differences from the browser timer, chosen
because a cube's face *is* the mode:

* When a countdown reaches zero the device switches to `FINISHED` and stays there.
  The next phase is **not** started automatically. The server computes
  `suggestedNextMode` from the pattern; the device can show it on its display and the
  website shows it on the start button. Flipping the cube (or a web command) starts
  the next phase.
* Starting the mode that matches the pattern position advances normally; starting a
  different mode is a manual override, like clicking a mode tab in the browser.

## 2. Device authentication

* After pairing the device receives a `deviceSecret` (43 chars, base64url, 256 bit)
  **once**. It must be stored in NVS. The server only stores its SHA-256 hash.
* Every device request (except `/api/devices/pair`) sends:

```
Authorization: Device <deviceSecret>
X-Device-Id: <hardwareId>
```

* `hardwareId` is an identifier, not a secret (for example the eFuse MAC as 12 hex
  chars). Only the secret proves identity.
* A device can only read and change its own data. User sessions and user JWTs are
  not accepted on device endpoints, and device secrets are not accepted on user
  endpoints.
* `401 DEVICE_UNAUTHORIZED` means the secret is unknown or revoked (the device was
  unbound or re-paired). The firmware must erase the secret and return to BLE
  provisioning mode.

## 3. Endpoints used by the device

Base URL is the `apiBaseUrl` received over BLE (for example `https://teclos.space`).

### 3.1 `POST /api/devices/pair` (no auth)

```json
{
  "pairingToken": "<token from BLE>",
  "hardwareId": "A1B2C3D4E5F6",
  "firmwareVersion": "0.1.0",
  "protocolVersion": 1,
  "name": "Pomodoro Cube",
  "capabilities": { "vibration": true, "sound": true, "rgb": true, "display": false, "imu": true }
}
```

`201 Created`:

```json
{
  "deviceId": 12,
  "deviceSecret": "q8D…",
  "serverTime": 1761150000000,
  "heartbeatIntervalSeconds": 30,
  "commandPollIntervalSeconds": 3
}
```

| Error | Code | Meaning |
|-------|------|---------|
| 400 | `PAIRING_TOKEN_INVALID` | Unknown token |
| 410 | `PAIRING_TOKEN_EXPIRED` | Older than 5 minutes |
| 409 | `PAIRING_TOKEN_USED` | Token was already claimed (one-time) |
| 409 | `DEVICE_OWNED_BY_ANOTHER_USER` | This `hardwareId` belongs to another account; it must be unbound there first |

Re-pairing a device that already belongs to the **same** user keeps its id, name,
settings and history and rotates the secret (the old one stops working immediately).

### 3.2 `POST /api/devices/heartbeat`

Every `heartbeatIntervalSeconds` (30 s). The device is shown `OFFLINE` when no
heartbeat or other device request arrives for `offlineAfterSeconds` (90 s).

```json
{
  "firmwareVersion": "0.1.0",
  "protocolVersion": 1,
  "capabilities": { "vibration": true, "sound": true, "rgb": true, "display": false, "imu": true },
  "metrics": { "wifiRssi": -61, "uptimeSeconds": 3600, "freeHeapBytes": 180000 },
  "face": "WORK",
  "state": { "...timer state snapshot..." }
}
```

* `metrics` — only values the hardware really measures. Unknown keys are ignored,
  missing keys are shown as "not reported". There is no battery field because the
  current hardware has no battery measurement.
* `state` is optional; when present it is treated like a `STATE_SYNC` event (3.4).

Response `200`:

```json
{
  "serverTime": 1761150000000,
  "pendingCommands": 1,
  "configHash": "5f2c…",
  "timerStateVersion": 7,
  "heartbeatIntervalSeconds": 30,
  "commandPollIntervalSeconds": 3
}
```

If `configHash` differs from the one the device stored, fetch `GET /api/device/config`.
If `pendingCommands > 0`, poll commands immediately.

### 3.3 `GET /api/device/config`

```json
{
  "configHash": "5f2c…",
  "timer": { "pomodoroMinutes": 25, "shortBreakMinutes": 5, "longBreakMinutes": 15,
             "pomoCycles": 4, "patternType": "classic" },
  "hardware": { "vibrationEnabled": true, "soundEnabled": true, "rgbBrightness": 60 },
  "faces": { "WORK": "START_WORK", "SHORT_BREAK": "START_SHORT_BREAK",
             "LONG_BREAK": "START_LONG_BREAK", "PAUSE": "PAUSE",
             "DISPLAY": "NONE", "TECH": "NONE" },
  "state": { "...current server timer state..." }
}
```

Timer durations come from the user's existing timer settings (`UserTimeSettings`),
hardware options from the device's `DeviceSettings`. Nothing is duplicated.

### 3.4 `POST /api/device/events`

Everything that happened on the cube, in order. Send immediately when online;
queue in RAM/NVS while offline and send the queue (oldest first) after reconnect.

```json
{
  "bootId": "7f3a91c2",
  "events": [
    {
      "eventId": "1d0e…uuid",
      "seq": 41,
      "type": "FACE_CHANGED",
      "face": "WORK",
      "occurredAt": 1761150000000,
      "state": { "...snapshot after the event..." }
    }
  ]
}
```

Event types: `FACE_CHANGED`, `TIMER_STARTED`, `TIMER_PAUSED`, `TIMER_RESUMED`,
`TIMER_STOPPED`, `TIMER_FINISHED`, `STATE_SYNC`.

* `eventId` — UUID, globally unique; the server ignores a repeated `eventId`
  (`DUPLICATE`), so resending the queue is always safe. The server keeps event ids for
  30 days, so a queue must not be replayed after a longer time offline.
* `bootId` + `seq` — `bootId` is random per boot, `seq` increases by 1 per event in
  that boot. Within one `bootId` an event whose `seq` is not greater than the last
  accepted one is ignored as `STALE`.
* `occurredAt` — device time after SNTP sync. If the clock was not synced yet, send
  `null`; the server uses its receive time. Timestamps in the future are clamped to
  the server time.
* `state` — the device's state after the event. If it is omitted on a `FACE_CHANGED`
  event, the server derives it with the face rules (section 5).

Response `200`:

```json
{
  "results": [ { "eventId": "1d0e…", "result": "APPLIED" } ],
  "state": { "...server timer state with version..." }
}
```

`result` is one of `APPLIED`, `DUPLICATE`, `STALE`, `IGNORED` (no state change, e.g.
`DISPLAY` face), `REJECTED` (invalid payload; `errorCode` explains).

### 3.5 Commands (website → device), HTTPS polling

`GET /api/device/commands` — returns commands that are waiting and not expired, oldest
first, and marks them `DELIVERED`. Poll every `commandPollIntervalSeconds` while
online (3 s), and immediately when a heartbeat reports `pendingCommands > 0`.

```json
{
  "commands": [
    { "commandId": "9a4c…uuid", "type": "PAUSE", "mode": null,
      "createdAt": 1761150000000, "expiresAt": 1761150030000 }
  ]
}
```

Command types: `START` (with `mode`), `PAUSE`, `RESUME`, `STOP`, `SWITCH_MODE` (with
`mode`, starts that mode immediately). At most one command per cube is open at a time.

`POST /api/device/commands/{commandId}/ack`

```json
{ "result": "EXECUTED", "errorCode": null, "state": { "...snapshot after execution..." } }
```

`result`: `EXECUTED` or `REJECTED` (`errorCode` e.g. `INVALID_STATE`). Acks are
idempotent: acking the same command again returns the stored result and changes
nothing. Expired commands must not be executed (`410 COMMAND_EXPIRED` on ack).

Command lifecycle: `PENDING → DELIVERED → EXECUTED | REJECTED`, or `EXPIRED` when
the device does not ack within 30 s. The website shows a command as done only after
`EXECUTED`.

Delivery is at-least-once: a `DELIVERED` command is returned again by the next poll
until it is acked (for example when the ack was lost). The firmware must remember the
ids and outcomes of the last 16 executed commands and, when it sees one of them again,
**re-send the stored ack without executing the command a second time**.

## 4. Version and reconnect rules

1. The device is the only writer of the timer state in Connected Device Mode. Every
   accepted event or ack increments `version` on the server.
2. Repeated `eventId` → `DUPLICATE`; repeated ack → same result; older `seq` in the
   same boot → `STALE`. None of them change state or create history twice.
3. After reconnect the device: (a) sends its event queue, (b) sends a heartbeat with
   its current `state`, (c) fetches config if `configHash` changed, (d) polls
   commands. Commands created while it was offline have expired by then and are
   never executed late.
4. The browser on WebSocket (re)connect always reloads the full snapshot over REST
   (`GET /api/devices/{id}/state`) and then applies WebSocket messages whose
   `version` is greater than what it has.

---

## 5. Cube face rules

Implemented on the server in `CubeFacePolicy` and mirrored by the emulator.

| Face | Current state | Result |
|------|---------------|--------|
| `WORK` / `SHORT_BREAK` / `LONG_BREAK` | same mode, `PAUSED` | resume |
| same | same mode, `RUNNING` | nothing |
| same | anything else | start that mode from full duration (a running or paused session of another mode is recorded as `INTERRUPTED`) |
| `PAUSE` | `RUNNING` | pause |
| `PAUSE` | otherwise | nothing |
| `DISPLAY`, `TECH` | any | nothing |

## 6. Session history

The server builds `PomodoroSession` rows from the device state stream:

* a new `sessionId` in `RUNNING` state opens a session (`IN_PROGRESS`);
* `FINISHED` closes it as `COMPLETED`, `STOPPED` or a new `sessionId` closes it as
  `INTERRUPTED`;
* `actualDuration` = seconds really counted down (pauses excluded);
* rows are unique per `(user, sessionId)`, so replays never create duplicates.

Browser sessions in Standalone Mode are posted by the web client to
`POST /api/pomodoro-sessions` with their own UUID and `deviceId = null`.

only receives messages, all actions go through REST with CSRF).
